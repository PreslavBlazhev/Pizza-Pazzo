# Онлайн плащане с карта — как работи и как се управлява

> Състояние към 2026-09-26: потокът е изграден и тестван **само с тестовия
> симулатор**. Банката на Pizza Pazzo още не е избрана, затова **няма банков
> адаптер и не е правен нито един тест през банка**. Картовото плащане е
> изключено по подразбиране навсякъде.

Свързани документи:
- [bank-meeting-checklist.md](bank-meeting-checklist.md) — какво да поискате от банката;
- [domain-and-deploy.md](domain-and-deploy.md) — `.com` домейнът, Render, staging.

## 1. Как работи (накратко)

```
checkout ──► Order { CARD_ONLINE, AWAITING_PAYMENT, releasedToKitchenAt = null }
             (кухнята НЕ я вижда, имейл НЕ се праща, кошницата остава)
   │
   ▼
/checkout/pay/{token}      наш екран: продукти, доставка, сума, „Плати с карта"
   │  POST /api/payments/start   (сумата е от базата, не от браузъра)
   ▼
хоствана страница на доставчика  (картата се въвежда САМО там; 3-D Secure)
   │                                  │
   ▼ браузърът се връща               ▼ сървърът на доставчика
/api/payments/return?t=…         /api/payments/callback/{provider}
   │                                  │
   └──────► syncAttempt: питаме доставчика server-to-server ◄──┘
                 │
     PAID + точната сума и валута?
                 │ да
                 ▼
   Order.paymentStatus = PAID → releasedToKitchenAt = сега → имейл към ресторанта
   (всяко от тези се случва ТОЧНО веднъж, колкото и заявки да дойдат)
```

- Статусът на **поръчката** (`status`: PENDING → ACCEPTED → … → DELIVERED) и
  статусът на **плащането** (`paymentStatus`: CASH_DUE / AWAITING_PAYMENT /
  PAID / FAILED / CANCELLED / EXPIRED) са две отделни колони.
- Всеки опит за плащане е ред в `PaymentAttempt`: вътрешна референция
  (`PP1012-3F9A1C2B`), доставчик, среда, id при доставчика, сума в центове,
  валута, статус, суров код на доставчика, времена. **Картови данни няма
  никъде.**
- Източникът на истина е **само** server-to-server проверката. Параметри като
  `?success=true`, самият факт на връщане на success URL или текст от
  браузъра не значат нищо.
- В брой: без промяна — поръчката отива в кухнята веднага, както досега.

### Какво пази от грешки

| Ситуация | Какво става |
|---|---|
| Двоен клик на „Завърши поръчката“ | един `checkoutKey` → една поръчка |
| Двоен клик на „Плати с карта“, back, втори таб | една отворена сесия при доставчика; всички кликове водят към нея |
| Повторен / закъснял callback, refresh, едновременни проверки | условни `updateMany` → една транзакция печели; кухня и имейл точно веднъж |
| Отказана карта | поръчката остава извън кухнята; „Опитай отново“ създава нов опит за **същата** поръчка |
| Изглеждало отказано, после банката потвърди | поръчката става PAID и отива в кухнята, маркирана „⚠ късно потвърждение“ |
| Две успешни плащания по една поръчка | и двете се пазят, поръчката е маркирана „ДВОЙНО ПЛАЩАНЕ“ — връщане ръчно през банката |
| Банката потвърди друга сума/валута | НЕ отива в кухнята; маркировка AMOUNT_MISMATCH |
| Платено след като персоналът е отказал поръчката | НЕ отива в кухнята; маркировка „за възстановяване“ |
| Банката не отговаря (timeout) | нищо не се променя; следващата проверка/callback решава |
| Клиентът затваря приложението/браузъра при банката | callback-ът пак завършва поръчката; сайтът и приложението показват „Поръчка №… чака плащане — провери“ |

Сайтът **никога** не връща пари и не отбелязва „възстановено“ сам. Връщане се
прави ръчно през портала на банката.

### Къде е кодът

| Файл | Какво |
|---|---|
| `lib/payments/config.ts` | всички env правила; кога картата е включена |
| `lib/payments/service.ts` | старт на плащане, проверка, финализиране, callback |
| `lib/payments/types.ts` | интерфейсът, който всеки доставчик изпълнява |
| `lib/payments/providers/simulator.ts` | тестовият симулатор |
| `lib/payments/providers/bank.ts` | **място за адаптера на банката** (сега връща „не е реализиран“) |
| `lib/checkout/place-order.ts` | създаване на поръчка (цени, идемпотентност) |
| `app/api/payments/*` | start / return / status / callback |
| `app/[locale]/checkout/pay/[token]`, `app/[locale]/payment/*` | екраните |
| `prisma/migrations/20260926175017_add_online_card_payments` | миграцията |

## 2. Променливи на средата

| Променлива | Стойност | Бележка |
|---|---|---|
| `APP_ENV` | `development` \| `staging` \| `production` | Липсва ли на production build → третира се като **production** |
| `APP_BASE_URL` | напр. `https://pizza-pazzo.onrender.com` | Единственият публичен адрес; от него са canonical, sitemap, return и callback |
| `CARD_PAYMENTS_ENABLED` | `true` / `false` | **Аварийният ключ.** По подразбиране изключено |
| `PAYMENT_PROVIDER` | `simulator` или `bank` | `bank` = бъдещият адаптер |
| `PAYMENT_ENV` | `sandbox` / `production` | Само за банка. sandbox е забранен при APP_ENV=production, production е позволен само при APP_ENV=production |
| `PAYMENT_CURRENCY` | `EUR` | Задължителна за банка (по договора). Сайтът таксува само в EUR |
| `PAYMENT_SIMULATOR_SECRET` | дълъг случаен низ (≥16) | Подписва callback-ите на симулатора |
| `STAGING_BASIC_AUTH` | `потребител:парола` | По избор; парола пред целия staging (не засяга `/api`) |

Правилата са в код и са тествани: **симулаторът не може да се включи при
`APP_ENV=production`**, а банков sandbox не може да приема поръчки в production.
Текущото състояние (включено/изключено, защо, точните return/callback адреси)
се вижда в **Админ → Настройки → „Онлайн плащане с карта“**.

## 3. Оперативни процедури

### 3.1. Staging и пълно демо плащане със симулатора

Staging е **отделна** Render услуга с **отделна** база. Никога не насочвайте
кухненския таблет към staging.

1. Render → New → Web Service от същото repo, клон `master`, същите build/start
   команди като production (`render.yaml`). Добавете Persistent Disk
   (`/var/data`, 1 GB).
2. Environment:
   ```
   APP_ENV=staging
   APP_BASE_URL=https://<staging-услугата>.onrender.com
   DATABASE_URL=file:/var/data/pizza-pazzo.db
   AUTH_SECRET=<нов случаен низ, различен от production>
   ADMIN_EMAIL=<ваш имейл>   ADMIN_PASSWORD=<временна парола>
   CARD_PAYMENTS_ENABLED=true
   PAYMENT_PROVIDER=simulator
   PAYMENT_SIMULATOR_SECRET=<дълъг случаен низ>
   STAGING_BASIC_AUTH=demo:<парола>          (по избор)
   ```
   Не задавайте `RESEND_API_KEY` на staging, ако не искате тестови имейли.
3. След първия deploy, от Render → Shell:
   `npm run db:seed` и `node scripts/import-menu-to-db.mjs`.
4. Отворете staging адреса → добавете пица → checkout → **„Плащане онлайн с
   карта“** → „Продължи към плащане с карта“ → екран „Преглед и плащане“ (с
   лилава лента ТЕСТОВ РЕЖИМ) → „Плати с карта“.
5. На жълтата страница на симулатора изберете сценарий:
   - **Успешно плащане** → „Плащането е успешно“, поръчката е в табло „Поръчки
     на живо“ с „ТЕСТ — НЕ ПРИГОТВЯЙ“ и „ПЛАТЕНО ОНЛАЙН С КАРТА — НЕ СЪБИРАЙ ПАРИ“;
   - **Отказана карта** / **Клиентът се отказва** → екран „Плащането не беше
     извършено“, поръчката НЕ е в таблото; „Опитай отново с карта“;
   - **Чакащо** → екран „Чакаме потвърждение“, обновява се сам;
   - **…потвърдено след 20 секунди** → чакащо, после само минава в „успешно“;
   - **Изглежда отказано, но банката го потвърждава** → късно потвърждение с ⚠ в админа;
   - **Банката не отговаря** → timeout, после успешно;
   - **Дублирани callback-и** / **Различна сума** → проверка на защитите.

Локално същото: в `.env.local`
```
APP_ENV=development
APP_BASE_URL=http://localhost:3000
CARD_PAYMENTS_ENABLED=true
PAYMENT_PROVIDER=simulator
PAYMENT_SIMULATOR_SECRET=local-demo-secret-0123456789
```
`npm run dev` → http://localhost:3000. Автоматична проверка на целия поток по
HTTP (сървърът трябва да работи със същите стойности):
`npm run e2e:payments`.

### 3.2. Смяна на домейна към `.com`

Вижте [domain-and-deploy.md](domain-and-deploy.md) — една променлива на сайта
(`APP_BASE_URL`), два реда в Android (`gradle.properties`) и новите адреси към банката.

### 3.3. Банков sandbox с тестова карта от банката

**Блокирано, докато нямаме официалната документация и sandbox достъпа.**
Когато ги получите:

1. Програмистът реализира `lib/payments/providers/bank.ts` по официалния
   протокол (указания има в самия файл), добавя тестове и новите env имена
   тук и в `.env.example`.
2. На **staging**:
   ```
   PAYMENT_PROVIDER=bank
   PAYMENT_ENV=sandbox
   PAYMENT_CURRENCY=EUR            (или каквото пише в договора — сайтът поддържа само EUR)
   <идентификаторите и ключовете от банката>
   ```
   Изтрийте `PAYMENT_SIMULATOR_SECRET`, не е нужен.
3. Дайте на банката адресите от Админ → Настройки (return и callback URL).
4. Платете с **тестова карта, дадена от банката** — успешно, отказано, отказ
   на страницата на банката, 3-D Secure. В нашата документация няма и не бива
   да има измислени тестови карти.

### 3.4. Проверка на резултата

- **Сайтът/клиентът**: екранът след банката казва „успешно“ само ако базата казва PAID.
- **Админ → Поръчки → поръчката**: значка „💳 Платено онлайн“ / „Чака плащане“ /
  „Неуспешно плащане“, секция „Плащане“ с всички опити (референция, статус,
  код на доставчика, сума, време) и бутон „Провери плащането при доставчика“.
  Референцията `PP…` е тази, която виждате и в портала на банката.
- **Кухня (Поръчки на живо)**: картова поръчка се появява само след
  потвърждение, с „ПЛАТЕНО ОНЛАЙН С КАРТА — НЕ СЪБИРАЙ ПАРИ“. Същото пише на бележката.
- **Отчет**: оборотът е разделен на „В брой“ и „Онлайн с карта“; „Платено
  онлайн“ е отделна карта; тестовите поръчки не се броят.
- **База** (Render → Shell, в папката на проекта):
  ```
  node -e "const{PrismaClient}=require('@prisma/client');const p=new PrismaClient();p.order.findMany({take:10,orderBy:{createdAt:'desc'},select:{orderNumber:true,paymentMethod:true,paymentStatus:true,releasedToKitchenAt:true,paymentAlert:true,isTest:true,paymentAttempts:{select:{reference:true,status:true,providerStatus:true,amountMinor:true,currency:true}}}}).then(r=>{console.dir(r,{depth:5});p.\$disconnect()})"
  ```
  Локално: `npm run db:studio`.

### 3.5. От банков sandbox към production

Само след успешни sandbox тестове (всички сценарии от 3.3) и подписан договор:

0. **Правните текстове** (с юрист/счетоводител): `content/legal/terms.ts`
   т. 4 и `content/legal/delivery.ts` т. 5 днес казват „само наложен платеж“ —
   вярно, докато картата е изключена. Преди включване: да опишат плащането с
   карта през страницата на банката, фискалния документ за платените онлайн
   поръчки и банката като обработващ картовите данни в
   `content/legal/privacy.ts`. `content/legal/refunds.ts` т. 7 вече казва, че
   картовите плащания се възстановяват по картата.
1. На **production** услугата:
   ```
   APP_ENV=production
   APP_BASE_URL=https://<окончателния домейн>
   PAYMENT_PROVIDER=bank
   PAYMENT_ENV=production
   PAYMENT_CURRENCY=<от договора>
   <production идентификаторите и ключовете — НЕ sandbox>
   CARD_PAYMENTS_ENABLED=false        ← първо изключено
   ```
2. Deploy. Админ → Настройки трябва да показва доставчик `bank / production`,
   без червени проблеми (освен „CARD_PAYMENTS_ENABLED не е true“).
3. Дайте на банката production return/callback адресите.
4. `CARD_PAYMENTS_ENABLED=true` → deploy. Направете една реална поръчка с
   малка сума със собствена карта, проверете админ/кухня/бележка/банков портал,
   откажете я и я възстановете през банката.

### 3.6. Аварийно изключване

Render → услугата → Environment → `CARD_PAYMENTS_ENABLED=false` → Save
(Render рестартира сама). Ефект за ~1 минута:
- checkout показва само „Плащане в брой при доставка“;
- нови картови плащания не се стартират (екранът за плащане показва съобщение);
- **вече започнати плащания продължават да се проверяват** — ако клиент е
  платил, поръчката му пак стига до кухнята.

Ако проблемът е в самия доставчик, изключете и `PAYMENT_PROVIDER` (празно) —
тогава и старите опити спират да се проверяват автоматично, а поръчките
остават „Чака плащане“ за ръчна проверка в портала на банката.
